# 음질 검증 보고서

이 문서는 MR MAKER 의 음질 관련 결정과 그 근거(직접 측정값·공개 벤치마크)를 정리합니다.
측정 스크립트는 저장소에 있어 누구나 다시 실행할 수 있습니다.

| 스크립트 | 내용 |
|---|---|
| `scripts/evaluate_separation.py` | 2-Stem 분리 품질 비교 (MUSDB18 7초 샘플 테스트 50곡, 정답 트랙 대비) — CI: *Actions → Evaluate* |
| `scripts/quality_report.py` | 원클릭 파이프라인 전체 검증 (YouTube 형식 입력 → 분리 → 키 → 저장, 실제 모델·실제 키 엔진) |
| `scripts/youtube_check.py` | 실제 YouTube 영상으로 스트림 선택·재인코딩 여부·리샘플 단계 확인 |
| `tests/test_quality.py` | 형식·리샘플·키·YouTube 선택 규칙·파이프라인 단위 테스트 (CI 에서 매번 실행) |

> 원칙: WAV·FLAC 으로 저장하거나 float32 로 처리한다고 원본에 없던 음질이 생기지는 않습니다. 목표는 **입력 음원과 AI 모델이
> 가진 품질을 처리 과정에서 깎아 먹지 않는 것**입니다. YouTube 오디오는 이미 손실 압축(Opus/AAC)된 음원이라 사라진 정보는 복원되지 않습니다.

## 1. 기존 구조에서 찾은 음질 저하 지점과 조치

| 위치 | 기존 | 문제 (측정) | 조치 |
|---|---|---|---|
| 디코딩·AI 입력 | FFmpeg `-ar 44100` (기본 swr 리샘플러) | 22.6kHz 성분이 **−15dB** 로 접혀 들어옴(앨리어싱), 20kHz −1.3dB 감쇠 | 원본 샘플레이트로 한 번 디코딩 → 44.1kHz 가 아닐 때만 **soxr VHQ** 로 1회 변환 (앨리어싱 −154dB, THD+N −151dB, 20kHz 감쇠 −0.002dB) |
| 저장 시 리샘플 | julius (sinc) | 20kHz THD+N −82dB, 22.6kHz 앨리어싱 −44dB | soxr VHQ. **보컬은 모델 출력(44.1kHz) 그대로 저장**(업샘플링 안 함), **MR 은 원본 샘플레이트에서 원본 − 보컬**(악기는 리샘플링 없음, 보컬 추정치만 1회 변환) |
| MP3 | `-b:a 320k -q:a 0` | `-q:a` 가 VBR(V0)로 바꿔 **실제 약 178kbps** 로 저장됨 | **CBR 320kbps** + LAME/Xing 헤더(인코더 지연 보정). 측정: 1136 프레임 모두 320kbps |
| FLAC | float → FFmpeg 가 24-bit 로 양자화 | WAV 24-bit 와 샘플값이 미세하게 다름 | WAV 24-bit 와 같은 반올림 정수를 그대로 전달 → **두 형식의 샘플이 비트 단위로 동일** |
| WAV 16-bit | 반올림만 | 양자화 왜곡이 음악과 상관됨 | TPDF 디더 |
| 피크 처리 | 샘플 피크 기준 | MP3 는 디코딩 시 샘플 사이 피크가 0dBFS 를 넘을 수 있음 | WAV/FLAC: 샘플 피크 ≤ −0.1dBFS, **MP3: 4배 오버샘플링 트루 피크 ≤ −1.0dBTP**(인코딩 후 다시 디코딩해 확인). 넘을 때만 **고정 배율**로 음량을 낮춤 (리미터·컴프레서·노멀라이즈 없음) |
| 키 변경 | Signalsmith Stretch (python-stretch) | 저음에서 음정 오차 6~30센트 (아래 4장) | **Rubber Band R3**, 선택한 결과물에 한 번만, 0 이면 처리 생략 |
| 분리 모델 | htdemucs (2-Stem) | 아래 2장 | **BS-RoFormer SW** (품질 우선, 기본), Demucs htdemucs_ft 보컬 모델 (속도 우선) |

이미 문제가 없었던 부분 (확인만 함)
- 디코딩은 처음부터 32-bit float (`pcm_f32le`) — 16-bit 정수 변환 없음
- 중간 결과는 float32 `.npy` (무손실) 로만 저장 — 중간 MP3 없음. 작업 폴더에 생기는 파일 형식: `.npy` 뿐 (검증 스크립트로 확인)
- 스테레오 유지 (모노 입력만 양쪽 채널로 복사, AI 모델이 스테레오 입력)

## 2. 2-Stem 분리 모델 비교

### 공개 벤치마크 — MVSEP Multisong 데이터셋 (같은 기준, 학습에 쓰이지 않은 곡)

| 모델 | 보컬 SDR | 반주 SDR | 라이선스 / 비고 |
|---|---|---|---|
| **BS-RoFormer SW** (6 stem) | **11.30** | **17.50** | 가중치 사용 조건 미명시 → 개인 용도 |
| MelBand RoFormer (Kimberley Jensen) | 11.01 | 17.32 | |
| BS-RoFormer (viperx edition) | 10.87 | 17.17 | |
| htdemucs_ft | 8.33 | 14.63 | MIT |
| htdemucs | 8.18 | 14.49 | MIT |

출처: [MVSEP Algorithms](https://mvsep.com/algorithms) (2026-10 확인). 더 높은 공개 모델(예: becruily 124 bands 12.25dB)도 있으나
배포처·라이선스를 확인하지 못해 제외했습니다.

### 직접 측정 — MUSDB18 7초 샘플 테스트 세트 50곡 (정답 트랙 대비)

GitHub Actions(4코어 CPU)에서 `scripts/evaluate_separation.py` 로 측정. 반주는 앱과 똑같이 '원본 − 보컬 추정'.

| 설정 | 보컬 SDR (평균/중앙) | 반주 SDR (평균/중앙) | MR 보컬 잔류 | 보컬 내 반주 누출 | 스테레오 폭 오차 | 처리 시간 (실시간 대비, CPU 4코어) |
|---|---|---|---|---|---|---|
| htdemucs (이전 버전 기본) | 8.23 / 8.15 | 13.47 / 13.27 | −21.3 dB | −20.4 dB | 0.34 dB | 0.38배 |
| htdemucs_ft 보컬 · 속도 우선 | 8.45 / 8.40 | 13.69 / 13.54 | −21.6 dB | −21.7 dB | 0.30 dB | 0.63배 |
| htdemucs_ft 보컬 · shifts 2 | 8.55 / 8.48 | 13.79 / 13.64 | −21.8 dB | −21.3 dB | 0.30 dB | 1.88배 |
| **BS-RoFormer SW · 품질 우선 (기본)** | **11.68 / 12.03** | **16.92 / 16.31** | **−28.6 dB** | **−26.7 dB** | 0.18 dB | 8.8배 |
| BS-RoFormer SW · 최고 품질 (겹침 4) | (측정 중) | | | | | |

- SDR = 10·log10(Σs² / Σ(s−ŝ)²), 높을수록 좋음. *MR 보컬 잔류* = MR 안에 남은 보컬 에너지 / 반주 에너지 (낮을수록 좋음),
  *보컬 내 반주 누출* = 보컬 추출물 안의 반주 / 보컬 에너지, *스테레오 폭 오차* = 정답 반주와 MR 의 Side/Mid 비 차이.
- 주의: BS-RoFormer SW 는 학습 데이터가 공개되지 않아 MUSDB18 테스트 곡이 학습에 쓰였을 가능성을 배제할 수 없습니다.
  그래서 학습과 무관한 MVSEP Multisong 수치를 함께 근거로 삼았고, 두 결과의 순위가 같습니다.
- Demucs 의 *shifts*(시간 이동 평균)는 2배로 늘리면 처리 시간이 3배가 되고 SDR 은 약 0.1dB 오릅니다.
  *overlap* 을 0.25 → 0.5 로 늘리는 것도 같은 수준입니다. 그래서 속도 우선 모드는 shifts 1 / overlap 0.25 로 둡니다.

### 결정

- **품질 우선(기본) = BS-RoFormer SW, 구간 겹침 2**. 보컬·반주 모두 Demucs 보다 약 3dB 좋습니다 (공개 벤치마크·직접 측정 모두).
  직접 측정에서도 보컬 SDR +3.2dB, 반주 SDR +3.2dB, MR 에 남는 보컬 −7dB (htdemucs_ft 대비).
  2-Stem 전용 모델이 아니라 6-Stem 모델이지만, 보컬 SDR 이 공개된 보컬 전용 모델들(10.9~11.0dB)보다 높아 그대로 씁니다.
  반주는 *원본 − 보컬* 로 만들어 악기 소리를 AI 가 다시 만들지 않으므로, 악기 고음·드럼 어택·베이스 저역·스테레오 이미지가 원본 그대로 남고
  (보컬 + MR = 원본, 오차 −135dBFS = 24-bit 양자화 수준) 차이는 보컬 추정 오차뿐입니다.
- **속도 우선 = htdemucs_ft 의 보컬 전용 하위 모델 1개** (htdemucs_ft 의 나머지 3개는 드럼/베이스/기타 전용이라 2-Stem 에 필요 없음 → 계산량 1/4).
  배포 파일에 포함되어 오프라인에서도 동작합니다.
- **최고 품질 = SW, 구간 겹침 4**: 처리 시간 약 2배.
- 처리 시간: BS-RoFormer SW 는 GPU(NVIDIA·Apple Silicon)에서는 곡 길이보다 짧게 끝나지만, CPU 만 있는 PC 에서는 곡 길이의 수 배~10배 이상 걸립니다
  (이 검증 환경 2코어 CPU 에서 27초 음원에 13분). 홈 화면은 CPU 로 처리할 때 파일을 고르면 예상 처리 시간을 보여 주고,
  진행 중에는 남은 시간과 *빠른 모드로 다시* 버튼을 보여 줍니다.

## 3. YouTube 오디오

### 스트림 선택 규칙 (`youtube.select_format`)
1. **오디오 전용 스트림**만 후보로 (영상 데이터는 받지 않음). 오디오 전용이 없을 때만 해상도가 가장 낮은 영상 포함 스트림.
2. 제외: **DRC**(음량 압축, 예: `251-drc`), DRM, 손상 표시, 해설(descriptive) 음성
3. 우선순위: 원래 언어 트랙 → 스테레오 이하 → 저비트레이트 보조 스트림(<96kbps) 아님 → **코덱 등급**(무손실 > Opus > Vorbis > AAC-LC > MP3 > HE-AAC)
   → 같은 코덱 안에서만 비트레이트·샘플레이트 비교. 즉 *AAC 256kbps vs Opus 130kbps* 처럼 서로 다른 코덱을 비트레이트 숫자로 비교하지 않습니다.
4. 받은 스트림은 **재인코딩하지 않고** 원래 컨테이너(WebM/M4A) 그대로 저장 (`postprocessors` 없음) → FFmpeg 로 float32 PCM 한 번 디코딩.

일반 공개 영상에서는 보통 `251` (Opus 약 130~160kbps, 48kHz, 20kHz 대역) 이 선택됩니다. `140` (AAC-LC 128kbps, 44.1kHz) 은
YouTube 인코딩 특성상 약 16kHz 이상이 잘려 있어 Opus 보다 낮게 둡니다. Opus 는 항상 48kHz 라 AI 입력용으로 44.1kHz 변환이 1회 필요하지만
soxr VHQ 의 오차(−150dB 수준)는 코덱 차이보다 훨씬 작습니다.

### 확인한 것
- 단위 테스트: 선택 규칙 9가지(DRC 제외, 코덱 등급, 저비트레이트 보조 스트림, 원어 트랙, 해설 음성, 다채널, 영상 포함 대체 …), 오류 메시지 분류 8가지
- YouTube 와 같은 형식(48kHz Opus 160kbps WebM)의 입력으로 전체 파이프라인 검증 (5장): 리샘플링은 AI 입력용 1회, 중간 손실 인코딩 0회
- yt-dlp 업데이트: GitHub 공식 배포본을 SHA-256 확인 후 저장, 번들 버전보다 새로울 때만 사용 (실제로 받아서 불러오기까지 확인)

### 확인하지 못한 것 (한계)
- **실제 YouTube 다운로드는 클라우드 검증 환경에서 확인하지 못했습니다.** GitHub Actions 서버 IP 에서 YouTube 가
  "Sign in to confirm you're not a bot" 으로 막았고(로그인·쿠키 우회는 하지 않음), 개발 환경은 YouTube 접속이 차단되어 있습니다.
  일반 PC 에서 `MRMaker --selftest --youtube-test <URL>` 또는 `python scripts/youtube_check.py` 로 선택된 코덱·비트레이트·샘플레이트와
  재인코딩 여부를 확인할 수 있고, 앱의 결과 화면에도 *입력: YouTube Opus 130kbps · 48kHz (오디오 전용 스트림, 재인코딩 없음)* 처럼 표시됩니다.

## 4. 키 변경

### 엔진 비교 (직접 측정, 44.1kHz)

음정 오차: 220Hz 배음 6개 신호의 각 배음 주파수 오차, 타이밍: 클릭 트랙 어택 위치 오차, 프리에코: 어택 직전 에너지(낮을수록 좋음),
왕복 LSD: +k 후 −k 로 되돌린 소리와 원본의 로그 스펙트럼 거리(낮을수록 좋음), 스테레오: 좌우 상관계수 변화.

| 지표 (+2 / −3 / +12 / −12) | Signalsmith (이전) | **Rubber Band R3 (현재)** |
|---|---|---|
| 음정 오차 (센트) | 6.7 / −1.1 / 4.0 / 11.4 | **0.0 / 0.0 / 0.0 / 0.0** |
| 배음 간 최대 편차 (센트) | 6.7 / 3.0 / 3.7 / 14.9 | **0.0 / 0.0 / 0.0 / 0.0** |
| 순음 음정 오차 55·110Hz (센트) | 8~9 / 17~33 / 4~15 / −6~−22 | **0.4 이하** |
| 타이밍 오차 (ms) | 0.2 / 0.4 / 0.3 / 3.5 | 0.3 / 2.6 / 2.9 / 5.0 |
| 프리에코 (dB) | −18.8 / −20.8 / −18.6 / −12.7 | **−38.9** / −18.6 / −16.2 / −8.6 |
| 왕복 LSD | 1.07 / 1.40 / **3.21** / 1.83 | **0.83 / 0.85** / 4.32 / **1.02** |
| 스테레오 상관 변화 | 0.005 / 0.013 / 0.009 / 0.023 | **0.0002 / 0.0009 / 0.0002 / 0.0053** |
| 처리 시간 (같은 음원) | 6.7초 | 39.5초 |

- 자주 쓰는 ±1~5 반음 구간에서 Rubber Band 가 음정·스펙트럼 왜곡·스테레오 보존 모두 좋습니다. Signalsmith 는 특히 **베이스 음역에서
  음정이 10~30센트 어긋나** MR 의 베이스가 다른 악기와 미세하게 맞지 않을 수 있습니다.
- ±12 같은 큰 변경은 두 엔진 모두 어느 지표에서든 손해가 커집니다 (+12 는 Rubber Band 의 LSD·프리에코가 더 나쁘고, −12 는 Signalsmith 의 음정 오차가 큼).
  범위는 −12 ~ +12 를 유지하되, 홈 화면에서 ±7 이상이면 *음질 변화가 커질 수 있다* 고 안내합니다.
- Rubber Band 는 GPL 이라 FFmpeg 처럼 별도 실행 파일(`rbshift`)로 호출합니다. 실행 파일이 없으면 Signalsmith 로 자동 대체됩니다.

### 포먼트(음색) 유지
- 말소리로 측정한 스펙트럼 포락선 이동: 포먼트 유지 끔 = 키만큼 이동(+2 → +2.25반음), 켬 = ±2~+12 에서 0~0.5반음 (−12 만 −11, 한계).
- 적용: **보컬 결과물은 기본으로 포먼트 유지**(목소리가 다람쥐·괴물 소리처럼 바뀌는 것 방지), **MR 은 끔**
  (악기는 음색까지 함께 옮기는 것이 자연스럽고, 유지하면 스테레오 상관 변화가 커짐). 고급 옵션에서 *보컬 음색(포먼트) 유지* 로 끌 수 있습니다.

### 파이프라인에서 확인 (5장 검증 스크립트)
- 키 0: 피치 처리 호출 **0회**, 결과가 이전 저장본과 **비트 단위로 동일**
- +2 / −3 / +12 / −12: 처리 1회(선택한 결과물에만), 길이 동일, 박자 어긋남 0ms, 측정된 음정 이동 **+2.0 / −3.0 / +12.0 / −12.0 반음**
  (MR 과 보컬 −3(포먼트 유지) 모두. 측정: 배음 봉우리만 남긴 로그 주파수 스펙트럼의 상호상관)

## 6. 남아 있는 한계

- **실제 YouTube 다운로드**는 검증 환경에서 확인하지 못했습니다 (3장). YouTube 가 바뀌면 yt-dlp 업데이트가 필요할 수 있습니다 (앱 안에서 가능).
- **BS-RoFormer SW 는 CPU 에서 느립니다.** 4분 곡이 8코어 PC 에서 대략 10~20분, 2코어에서는 30분 이상 걸릴 수 있습니다. GPU 가 없으면 속도 우선 모드를 권장합니다.
- **SW 가중치의 사용 조건이 명시되어 있지 않아** 음악 모임 안의 개인 연습용으로만 쓰는 것을 전제로 합니다 (상업적 이용 불가).
- 분리 품질은 곡에 따라 크게 다릅니다 (곡별 SDR 편차가 큼). 리버브가 강한 보컬, 보컬과 같은 음역의 리드 악기, 화음(코러스)은 일부가 반대쪽에 남을 수 있습니다.
- 키를 크게 바꾸면(±7 이상) 어떤 알고리즘이든 어택이 흐려지거나 음색이 달라질 수 있습니다.
- 청취 평가는 자동화하지 못해 수치 지표(SDR, 잔류·누출 에너지, 음정·타이밍 오차, 스펙트럼 거리)로 대신했습니다.
